# 37 · 步数预算实验：耗尽是症状，编辑自伤才是病因

- 日期：2026-08-04
- 相关：[35](35-agent-arena-claude-vs-deepseek.md) [36](36-scope-constraint-ablation.md)
- 原始数据：`bench_reports/ablation-scope-20260804.json`（对照组，`max_steps` 用题目自带值）、
  `bench_reports/steps30-20260804.json`（实验组，`--max-steps 30`）

## TL;DR

**加大步数预算是无效干预，可能还有害。** `max_steps` 从各题自带的 14–20 统一提到 30：

- pass_rate 0.733 → 0.800，但 **10 道题翻转（6 fix / 4 regression）**，而实测噪声底是
  ±3 题。**这个 +6.7 点不构成证据。**
- **只有 1 道题真正用到了超出原预算的步数**（`packaging_ci_contract`，21 步 > 原上限
  20），而它仍然失败。另外 3 道"被买回"的题这次分别只用了 9 / 13 / 16 步——
  **比它们原来的上限还少**。预算根本没绑定。
- 那 3 题翻转的真实原因是**这一轮没有陷入编辑自伤**：这 4 题的自伤次数 7 → 2。
- 放宽预算的净副作用：**全局自伤次数 13 → 25，几乎翻倍**。`filename_sanitizer`
  从 10 步 PASS 退化成自伤 6 次、跑满 30 步失败。
- 成本 +30.6% token。

真正的瓶颈是 **`edit_file` 的行号编辑自伤**：agent 拿着读文件时的行号去替换，
而行号在上一次编辑后已经失效，于是把文件改坏，再花 3–6 步修自己——通常还会再错一次。
6/30 题出现过，占失败题的一半。

## Context

[devlog 36](36-scope-constraint-ablation.md) 把「改了不该改的文件」清零之后，
首要失败模式换成了**步数耗尽：4 题，其中 3 题的隐藏测试已经通过**——
代码写完了，只是没走到 `finish`。表面上这像个纯预算问题：把上限调高就该买回来。

动手之前先读了这 4 题的 trace。**它们根本不是同一种失败。**

### 一题是真的差 1 步

`cross_file_user_contract`（预算 18 步，用满 18 步，隐藏测试通过）：

```
step16 run_tests   所有边界情况都正确处理了……现在重新运行可见测试确认没有破坏现有行为。
step17 read_file   可见测试通过，边界情况也验证正确。确认最终文件内容，然后完成任务。
step18 read_file   确认 serializers.py 的最终内容。
                   ← 第 19 步就是 finish，预算没了
```

thought 里明写着「然后完成任务」。这是教科书级的预算问题。

### 另外三题是 agent 把文件改坏了，然后在修自己

`semver_compare`（coding，预算 16 步用满）：

```
step10 read_file   发现 '1.2.3-' 没有抛出 ValueError……需要修复
step11 edit_file   修复 _parse_version
step13 read_file   编辑时替换了错误的行，导致 core 变量定义丢失。需要读取当前文件确认状态并修复。
step14 edit_file   确认问题：第 8 行缺少 `core = parts[0]`。需要插入该行。
step16 edit_file   插入位置错误，`core = parts[0]` 被插入到了 if 语句内部且缩进错误。
```

`cli_config_docs_contract`（预算 18 步用满）：

```
step14 create_file 我的替换操作出错了。原来的文件行号与我预期的不一致，导致替换时把
                   CONFIG_OPTIONS 的一部分也替换掉了。现在文件损坏了。
step16 read_file   测试文件出现了问题……这可能是我的替换操作把原有测试函数的一部分残留下来了。
step17 edit_file   测试文件末尾残留了一行……需要删除这一行。
```

两段 thought 指向同一个机制：**`edit_file` 按行号编辑，而行号在上一次编辑之后就失效了。**
agent 拿着读文件时看到的行号去替换，替换到了错误的区间，把文件改坏，然后花 3–6 步
修复自己造成的破坏——通常还会再错一次。

### 这不是个别现象

扫全部 30 份 trace，统计 thought 里承认「文件损坏 / 替换出错 / 行号不一致 /
插入位置错误 / 残留」的步骤：

| 任务 | 自伤次数 | 最终 | 步数 |
| --- | ---: | --- | ---: |
| `cli_config_docs_contract` | 4 | 步数耗尽 | 18 |
| `csv_row_parser` | 2 | PASS | 16 |
| `parse_duration` | 2 | PASS | 12 |
| `semver_compare` | 2 | 步数耗尽 | 16 |
| `ttl_cache_lru` | 2 | 隐藏测试没过 | 18 |
| `packaging_ci_contract` | 1 | 步数耗尽 | 20 |

**6/30 题出现过，其中 4 题最终失败——而全套只有 8 题失败。一半的失败题都经历过编辑自伤。**
4 道步数耗尽题里有 3 道在列。自伤是可恢复的（`csv_row_parser`、`parse_duration` 恢复后
仍然 PASS），但每次都要付出好几步。

所以「加大预算」这个干预，真正在测的是：**自伤循环能不能在更宽的预算里收敛。**
如果能，那步数耗尽确实主要是预算问题；如果不能，加预算只是延长痛苦，真正该修的是
编辑工具的用法。

## 实验设计

一个变量：`--max-steps 30`，统一覆盖各题自带的 14–20。其余与 devlog 36 的实验组完全一致
（同模型、同温度、同 `--declare-allowed-files`、同判分、同任务集）。

**`max_steps` 不进 prompt。** 查过 `core/prompting.py` 与 `core/context_window.py`：
交给模型的内容里没有步数预算、也没有剩余步数，只有 plan 步骤。所以放宽上限**不会**
改变 agent 的行为倾向，它纯粹是把截断点后移。这给了一个免费的对照检验：
**原本就通过的题，步数应该几乎不变**——若它们也涨了，说明有别的东西在漂。

主指标刻意选了不受总分噪声影响的三个：

1. 步数耗尽的题数；
2. 原本耗尽的题这次**实际用了多少步收尾**（差 1 步还是仍然用满 30 步）；
3. 是否出现 `finish` 动作。

pass_rate 只作次指标看：devlog 36 实测噪声底是 **±3 题 ≈ ±10 个百分点**，
而这个干预理论上限只有 4 题，信噪比 1.3:1，单跑一轮的总分差异不构成证据。

### 复现

```bash
python -m dm_agent.benchmarks.cli --suite all --declare-allowed-files --max-steps 30 \
  --trace-dir bench_reports/steps30-traces \
  --output bench_reports/steps30-20260804.json \
  --markdown bench_reports/steps30-20260804.md

python -m dm_agent.benchmarks.score_diff \
  bench_reports/ablation-scope-20260804.json \
  bench_reports/steps30-20260804.json
```

## 结果

| 指标 | 对照组（自带预算） | 实验组（30 步） |
| --- | ---: | ---: |
| pass_rate | 0.733 (22/30) | 0.800 (24/30) |
| hidden_test_pass_rate | 0.833 | 0.900 |
| 步数耗尽 | 4 | 1 |
| 隐藏测试没过 | 4 | 4 |
| 改了不该改的文件 | 0 | **1** |
| 平均步数 | 11.7 | 14.2 |
| tokens | 1,458,155 | 1,903,954（**+30.6%**）|
| **翻转题数** | — | **10（6 fix / 4 regression）** |

**总分上升 6.7 点，但翻转了 10 题，而噪声底是 ±3 题。这个差异不构成证据。**
下面三条把「不构成证据」从口号变成了具体的机制。

### 主指标 1：预算根本没绑定

原本步数耗尽的 4 题，这次实际用了多少步：

| 任务 | 原上限 | 对照组用量 | 实验组用量 | 结果 |
| --- | ---: | ---: | ---: | --- |
| `semver_compare` | 16 | 16（用满） | **9** | PASS |
| `cross_file_user_contract` | 18 | 18（用满） | **13** | PASS |
| `cli_config_docs_contract` | 18 | 18（用满） | **16** | PASS |
| `packaging_ci_contract` | 20 | 20（用满） | 21 | 仍失败 |

**三道题在原来的预算内就做完了。** 如果它们的失败真是「差几步」，实验组应该看到
19–21 步收尾；实际是 9–16 步——完全不同的轨迹。**唯一真正吃到超额预算的
`packaging_ci_contract`（21 步）依然失败。**

换句话说：这个干预的因果效应约等于零。三题的翻转必须由别的东西解释。

### 主指标 2：解释是自伤，不是预算

同样这 4 题，thought 里承认「文件损坏 / 替换出错 / 行号不一致」的次数：

| 任务 | 对照组自伤 | 实验组自伤 | 结果变化 |
| --- | ---: | ---: | --- |
| `semver_compare` | 2 | **0** | 耗尽 → PASS（9 步） |
| `cross_file_user_contract` | 0 | 0 | 耗尽 → PASS（13 步） |
| `cli_config_docs_contract` | 4 | 2 | 耗尽 → PASS |
| `packaging_ci_contract` | 1 | 0 | 仍失败（隐藏测试） |
| 合计 | **7** | **2** | |

`semver_compare` 是最干净的一例：对照组自伤 2 次、用满 16 步失败；实验组自伤 0 次、
9 步通过。**变量不是预算，是这一轮有没有踩到行号失效。**

`cross_file_user_contract` 是四题里唯一真的「差 1 步」的（对照组自伤 0 次，
thought 明写「然后完成任务」）。但它实验组用了 13 步而非 19 步——连它的翻转
都不能归因于加预算。

### 主指标 3：放宽预算让自伤更多，不是更少

全局统计，两组各 30 份 trace：

| | 对照组 | 实验组 |
| --- | ---: | ---: |
| 出现自伤的题 | 6/30 | **9/30** |
| 自伤总次数 | 13 | **25** |

**更多步数 = 更多编辑机会 = 更多自伤。** 四道回归题里两道就是这么来的：

| 回归题 | 自伤 | 步数 | 结局 |
| --- | ---: | ---: | --- |
| `filename_sanitizer` | 0 → **6** | 10 → **30** | PASS → 步数耗尽 |
| `error_propagation_contract` | 0 → 2 | 11 → **30** | PASS → JSON 解析失败 |
| `inventory_reservations` | 0 → 0 | 10 → 8 | PASS → 隐藏测试没过（纯随机） |
| `sql_where_builder` | 0 → 0 | 9 → **20** | PASS → **违规** |

`filename_sanitizer` 是完整的反面案例：对照组 10 步干净通过，实验组自伤 6 次、
把 30 步全部烧光。**在旧预算下它会更早被截断——结果一样是失败，但便宜得多。**

### 对照检验失败了，这本身是结果

设计时预期「原本就通过的题步数应该几乎不变」，因为 `max_steps` 不进 prompt。
实际只有 **11/22** 题的步数变化在 ±2 以内。原本 6 步通过的 `order_total_edges`
这次用了 11 步，8 步的 `safe_int_parse` 用了 15 步。

我回去把这条路径又查了一遍确认没看漏：`limit` 只用于循环边界、checkpoint 与
trace metadata；`RunContext` 没有这个字段；`planner.py` 里的 `"max_steps"` 是
adaptive replanning 的**失败信号种类名**（且该能力默认关闭），不是预算值。
**agent 确实不知道自己的预算。**

所以这些步数漂移只能是运行间方差——**DeepSeek 在 temperature=0 下的方差比
devlog 36 估计的还大**。同一道题、同一段 prompt，能 6 步做完也能 11 步做完。
这条否定的对照，比实验本身的正向结果更有价值。

### 一条要补进 devlog 36 的更正

`sql_where_builder` 在 `--declare-allowed-files` 开着的情况下**仍然违规**了：
新建了 `tests/test_query_comprehensive.py`。所以 devlog 36 的「8 → 0」不是一条
绝对定律，而是一次采样：**违规率是低但非零**，两轮实验合计 60 次运行里出现 1 次。
结论方向不变，力度要下调。

## 结论

1. **步数预算不是瓶颈。** 拿掉它（14–20 → 30）没有产生可归因的收益，代价是
   +30.6% token 和翻倍的自伤。想提分不该往这里投。
2. **真正的瓶颈是 `edit_file` 的行号编辑自伤。** 6/30 题踩到，占失败题的一半；
   四道步数耗尽题里三道由它驱动。它把「步数不够」这个症状制造了出来——
   agent 不是走得慢，是走了回头路去修自己。
3. **「步数耗尽」这个失败标签具有误导性。** 它记录的是截断发生了，不是原因。
   两种截然不同的故事（差 1 步 vs 自伤循环）被归进同一个桶，直接看标签会
   得出「加预算」这个错误处方。**失败分类必须能追到机制，否则它会指错方向。**
4. **单跑一轮测不出 4 题级别的效应。** 这次翻转 10 题、噪声底 ±3 题，
   +6.7 点被完全淹没。devlog 36 那个 +23.3 点（违规 8 → 0，主指标是计数不是分数）
   之所以站得住，正是因为它的效应量远大于噪声、且有不受噪声影响的直接指标。

## Open questions / next bets

1. **修 `edit_file` 的自伤，这是当前最高杠杆。** 行号在编辑后失效是机制性的，不是
   模型不小心。可选方向：改成字符串精确匹配（`old_string` / `new_string`，匹配不到
   就报错而不是改错位置）、编辑后自动回显受影响区间、或在 `after_tool_result` 上挂
   语法校验。**前两个是工具契约变更（要动 `dm_agent/tools/file_tools.py`），第三个
   可以先写成外部扩展验证收益**——按项目惯例应该先做便宜的那个。
2. **任何后续实验都需要 `--repeat 3`。** 已经有两次教训：噪声底 ±3 题会淹没
   4 题以下的效应。代价是三倍 token，但没有它就只能测「违规归零」这种量级的效应。
3. **`max_steps` 要不要进 prompt？** agent 现在完全不知道预算，因此无法在快用完时
   收敛（「先保证交付一个可用版本」）。这是一个独立的、可证伪的假设，但要先修
   自伤——否则又是在给一个被别的东西主导的指标做微调。
4. 实验组的 `steps30-20260804.json` **不建议当作新 baseline**：0.800 是噪声上沿，
   不是真实水平。基线仍应是 `ablation-scope-20260804.json` 的 0.733。
