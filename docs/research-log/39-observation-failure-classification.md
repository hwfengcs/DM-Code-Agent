# 39 · 失败判定的来源分层，与第一次带误差棒的水位

- 日期：2026-08-05
- 相关：[36](36-scope-constraint-ablation.md) [37](37-step-budget-and-edit-self-damage.md)
  [38](38-edit-file-precision.md) [33](33-scope-reduction.md)

## 一句话

把「这条观察算不算失败」从全文扫描改成按来源分层，误报 replan 归零；顺手发现并修掉
`run_linter` 撞墙与一个 Windows 行尾缺陷；第一次用 `--repeat 3` 拿到带误差棒的水位
**0.878**，同时把噪声底从「±3 题」上修到 **±5 题**。

## 病灶：判定在扫描工具搬运的内容

`core/observation.py` 的 `FAILURE_MARKERS` 里躺着裸子串 `"error"`。观察文本里其实
混着两种东西：

- 工具**自述**的状态：`文件 x.py 不存在。`、`Tool execution failed: ...`
- 工具**搬运**的外部内容：文件正文、子进程 stdout、编辑回显

全文扫描对两者一视同仁，于是读到一行 `from errors import NotFound` 就把一次成功的
`read_file` 判成失败，白烧一次 planner 调用。

用 devlog 38 那一轮的 30 份 trace 复算，296 次工具调用里 84 次被判失败，**38 次是
误报**；按 replan 口径是 78 次里 34 次（43.6%）。

其中最大的一块（18 次）来自 devlog 38 给 `edit_file` 加的编辑回显——它把文件正文
带进了观察。**devlog 38 已经把这笔代价记在了「代价栏」**（replan 58 → 78，其中
17 次由回显触发，根因写明是 `from errors import` 命中 `FAILURE_MARKERS`）。
它记的 17 次是"回显触发"这一个口径，本篇的 34 次是"全部误报"口径，两者不矛盾。
所以这不是一次翻案，是**去还 devlog 38 当时就挂在账上的债**。

| 误报来源 | 次数 |
| --- | ---: |
| `edit_file` 回显里的 `Error` 标识符 | 18 |
| `read_file` 读到的 `errors` 模块 / `test_..._errors` | 12 |
| `run_python` 脚本自己打印的 `ERROR:`（`returncode: 0`） | 6 |
| `list_directory` 列出一个叫 `errors.py` 的文件 | 1 |
| `run_tests` 输出里的 error 字样（退出码为 0） | 1 |

值得记一笔的是这条因果链的形状：devlog 38 修好编辑自伤（13 → 0）**的同时**放大了
另一个既存缺陷（误报 replan ~16 → 34）。两者都真实，且它当时就诚实地写下来了——
本篇能一步定位，靠的就是那份记录。

## 改法

按来源分层，只在工具自述的位置上判定：

1. 内核自述的失败前缀（`Tool execution failed` / `Unknown tool` / ...）
2. `[语法检查] 未通过：`——写入落盘了但代码是坏的，仍须重规划
3. **子进程退出码是权威信号**：锚定行首行尾的 `returncode: N`，压过正文里出现的
   任何 `error`/`Traceback`（那可能只是探测脚本打印的预期输出）
4. 内置工具「没能完成请求」的自述句式（整条观察就是这一句，不夹带正文）
5. 内置工具的其余观察一律不算失败
6. 第三方扩展工具的输出格式内核无从保证，仍走原来的全文扫描，行为不变

第 5 条是关键翻转：**默认不失败**，而不是默认扫描全文。第 6 条保证这不是一次
破坏性变更。`_STRUCTURED_OUTPUT_TOOLS` 与 `_builtin_tools()` 的一致性由测试断言，
新增内置工具时会被提醒确认其输出契约。

同一批 trace 复算：**误报 38 → 0，46 次真失败全部保住**，另外多抓到 4 次旧判定
漏判的真失败——3 次 `路径 tests 不是文件。`（"不是文件"不在旧 marker 里），
1 次 `returncode: 255`（旧实现只认字面量 `returncode: 1`，255 靠子串巧合才命中）。
零反向误报。

## 捎带修掉的两个

**`run_linter` 撞墙。** 默认检查器硬编码 `flake8`，而项目自己的 `.venv` 里装的是
ruff。39 次调用里 **29 次**撞在没装的 flake8/pylint 上，横跨 **15/30 道题**，
占该轮 325 总步数的 8.9%，且每次各自触发一次 replan。模型拿到裸的
`No module named` 只会挨个盲试下一个（一道题平均撞两次）。改为报出本环境实际可用的
清单，文案避开失败标记——换一个检查器重试是局部纠正，不该白烧一次重规划。

**Windows 行尾。** 这个是跑 SWE-bench 时才暴露的：`Path.write_text` 默认的
`newline=None` 会把 `\n` 改写成 `os.linesep`，于是编辑一个 LF 文件会把整份文件转成
CRLF。在 astropy 上改一处逻辑，patch 是 20595 字节 `+317/-317`；修复后 504 字节
`+1/-1`。本地 30 题 benchmark 看不到它——那些工作区文件都是新建的，行尾自始至终
一致，**要有一个外部的真实仓库才暴露得出来**。

## 结果：单轮说谎，三轮说话

单轮（`obsfix-20260805`）的主指标全部达标：

| 指标 | 前 | 后 |
| --- | ---: | ---: |
| 失败观察 | 84 | 12（−85.7%） |
| replan | 78 | 23（−70.5%） |
| `run_linter` 撞墙 | 29 | **0** |
| 步数 / token | 325 | 305（−6.2%）/ −10.0% |

但 pass_rate 是 **0.833 → 0.767**，翻转 6 题。按 devlog 37 的教训，这在噪声内，
不构成证据——于是第一次跑 `--repeat 3`（90 次 run）：

| 分类 | 题数 |
| --- | ---: |
| 3/3 稳定通过 | 24 |
| 2/3 抖动 | 4 |
| 0/3 稳定失败 | 2 |

- **真实水位 0.878**，不是单轮那个 0.767。单轮抽到的是运气差的一次。
- `pass@3 = 0.933` vs `pass^3 = 0.767`，**差 0.167 = 5 道题**在多轮之间来回翻。
  噪声底从 devlog 37 的「±3 题」上修到 **±5 题 ≈ ±16.7 个百分点**。
- 抖动的 4 题里有 3 题正是单轮里"回归"的那批——**不是回归，是抖动**。
- 原先步数耗尽的 3 题（`cross_file_user_contract` / `filename_sanitizer` /
  `normalize_users`）现在全部 3/3 稳定通过。**误报重规划吃掉的步数就是它们的死因**，
  这也回过头解释了 devlog 37「加步数预算无效」为什么是对的：病根不在预算。
- 稳定失败的 2 题与 devlog 38 判定的"真实能力不足"完全吻合。

## 教训

**这一轮真正的产出不是 +4.5 个百分点，是知道了 ±16.7 个百分点以内的差异都不算数。**
前三轮（36/37/38）全部是单轮实验，其中 devlog 37 的 +6.7 点被判为"不构成证据"是
侥幸判对了——按现在测出的噪声底，那个判断本来就该是"不可能构成证据"。

推论：**30 题这个盘子测不出 5 题以内的改进**。要么加题，要么所有实验都跑
`--repeat 3`，要么继续只信直接计数型主指标（违规题数、撞墙次数、误报次数）——
这三轮能站得住，靠的一直是第三条。

## 回填更正

- devlog 37 的「噪声底 ±3 题 ≈ ±10 个百分点」上修为 **±5 题 ≈ ±16.7 个百分点**
  （首次 `--repeat 3` 实测，`pass@3 - pass^3 = 0.167`）。
- devlog 38 的「代价栏」记的 17 次是"回显触发的 replan"口径；全部误报是 34 次。
  两者不矛盾，本篇按后者统计。**该栏的记录本身是准确的**，本篇是去还那笔债。
- 本篇初稿曾写「devlog 38 没记到这个代价、交接记录低估了一半」，**这两句都是错的**
  ——devlog 38 的代价栏写得很完整，连根因都点明了。已更正为上面的口径说明。
