# 38 · 修 `edit_file` 的编辑自伤：按内容定位 + 编辑后回显

- 日期：2026-08-04
- 相关：[36](36-scope-constraint-ablation.md) [37](37-step-budget-and-edit-self-damage.md)
- 原始数据：`bench_reports/ablation-scope-20260804.json`（对照组）、

## TL;DR

**编辑自伤 13 次 / 6 题 → 0 次 / 0 题。** 模型 **100%（47/47）主动改用了按内容定位**，
零未命中——一次都没退回行号模式。

devlog 37 诊断为「自伤驱动的步数耗尽」那三题，链条被逐一验证：

| 任务 | 对照组 | 实验组 |
| --- | --- | --- |
| `semver_compare` | 步数耗尽（16 步用满） | **PASS**（14 步） |
| `cli_config_docs_contract` | 步数耗尽（18 步用满） | **PASS（9 步）** |
| `packaging_ci_contract` | 步数耗尽（20 步用满） | 隐藏测试没过（15 步）——露出真实死因 |

顺带：`edit_file` 调用数 63 → 47（**−25%**，不用再修自己了），总步数 −7.1%，
token **−3.9%**。pass_rate 0.733 → 0.833，但翻转 7 题、噪声底 ±3 题，
**分数不作为独立结论**——主指标才是。

代价栏：**replan 58 → 78**，其中 **17 次由回显触发**——回显把代码内容带进
observation，里面的 `from errors import` / `raise ValueError` 命中了
`FAILURE_MARKERS`，一次成功的编辑被误判成失败。见「诚实栏」。

## Context

[devlog 37](37-step-budget-and-edit-self-damage.md) 排除了「步数预算不够」这个假设，
并把矛头指向 `edit_file`：6/30 题出现编辑自伤，占失败题的一半，四道步数耗尽题里
三道由它驱动。这次修它。

### 机制：不是行号过期，是区间选错 + 没有回执

先排除了一个看似显然的解释：**`ReadBeforeEditGuard` 已经在拦 stale_read**
（`core/guards.py`），编辑前没读过、或读完文件又变了，都会被挡下并提示重读。
所以自伤不是「拿着过期行号去编辑」。

真正的机制是两件事叠加：

1. **一次性把区间选错。** `replace` 执行的是
   ```python
   lines[start_idx:end_idx] = [content]
   ```
   整个区间被一个 content 顶掉。模型想只换第 6 行、把区间写成 5–6，第 5 行就被
   静默吞掉。`semver_compare` 正是这样丢了 `core = parts[0]`——语法完全合法，
   测试要到几步之后才炸。

2. **返回值不含任何结果信息。** 旧回执只有一句「已替换 semver.py 的第 5-6 行。」
   模型没有任何依据判断自己改对没有，于是继续往下走。

实测**自伤到被发现平均隔 2.2 步**（n=13，分布 1–3），发现后还要 3–6 步修复，
而且经常再错一次——`semver_compare` 的 step16 就是在修 step11 造成的破坏时
又插错了缩进。

## 两处干预

一个防、一个查，作用点不同：

| | 时机 | 能抓什么 |
| --- | --- | --- |
| A. 按内容定位替换 | **事前防止** | 从机制上不可能吞掉相邻行 |
| B. 编辑后回显 | **事后立刻发现** | 把 2.2 步的发现延迟压到 0 |
| B'. `.py` 语法检查 | 事后立刻发现 | 只抓语法崩坏，见下方能力边界 |

### A. `old_string` / `new_string`

```json
{"path": "semver.py",
 "old_string": "    prerelease = parts[1] if len(parts) == 2 else None",
 "new_string": "    prerelease = parts[1] if len(parts) == 2 else None\n    ..."}
```

`old_string` 必须**逐字命中且仅命中一次**（含空白与缩进）。命中 0 处或多处时
**文件一个字节都不动**，返回提示让模型带更多上下文重试。与
`operation`/`line_start`/`line_end` 互斥；不传就走原来的行号模式，向后兼容。

### B. 回显受影响区间

```
已按内容替换 semver.py 的 1 处（52 -> 78 字符）。
[编辑后] 第 2-6 行（共 6 行）：
     2 |     parts = version.split('-')
     3 |     if len(parts) > 2:
     4 |         raise ValueError('bad')
>    5 |     prerelease = parts[1] if len(parts) == 2 else None
     6 |     return core, prerelease
```

带**新**行号，改动行用 `>` 标出，上下各 3 行上下文，总长上限 40 行
（`--max-observation-chars` 是全局兜底，不该指望它处理这里本可精确控制的情况）。

上面这段正是 `semver_compare` 自伤的复现：第 4 行之后直接跳到 `prerelease`，
`core = parts[0]` 不见了——**模型当步就能看出来**，不必等测试炸。

### 关于 `ast.parse` 能力边界的诚实说明

`.py` 文件额外过一遍 `ast.parse`，**只报告不回滚**（分步编辑的中间态可能合法地
无法解析，回滚会让工具变得不可预测）。但它的能力必须说清楚，
`semver_compare` 那两次自伤正好各占一边：

- step16「插入位置错误、缩进错误」→ **抓得到**；
- step13「`core` 变量定义丢失」→ 语法完全合法，**抓不到**。

所以**回显是主力，语法检查是辅助**。把 B' 说成「自动检测编辑错误」是夸大。

### 一条容易踩的内核约束

`core/observation.py` 的 `FAILURE_MARKERS` 含「失败/错误/error/不存在」，
命中就会触发一次完整重规划。模块注释明确写着内核护栏文案要**刻意避开**这些词
——`core/guards.py:_block_message` 就是这么写的。

所以 `old_string` 未命中/多处命中的提示措辞照此办理（用「未命中」「未替换」），
因为那是模型下一步就能自行纠正的局部问题，不该惊动 planner。

**但回显本身绕不开这条**：它把文件内容带进 observation，而被编辑的代码里
出现 `raise ValueError` 这类字样是家常便饭，一旦出现就会命中 `Error`。
这是本次改动已知的副作用，实验里单独量了 replan 次数——见「诚实栏」。
（顺带发现：`read_file` 读到含 error 字样的文件同样会触发，这是既有的
系统性问题，不是本次引入的。）

## 实验

一个变量：只换了 `edit_file` 的实现与工具描述，其余与 devlog 36 的实验组完全一致
（同模型、同温度、同 `--declare-allowed-files`、各题自带步数预算、同判分、同任务集）。
工具改动不进 manifest，`suite_signature` 不变，`dm-agent-score-diff` 直接可用。

```bash
python -m dm_agent.benchmarks.cli --suite all --declare-allowed-files \
  --trace-dir bench_reports/editfix-traces \
  --output bench_reports/editfix-20260804.json \
  --markdown bench_reports/editfix-20260804.md
```

**主指标（机制级，不受 pass/fail 噪声影响）：**

1. 自伤次数（对照组 13 次 / 6 题）
2. 自伤到被发现的步数间隔（对照组 2.2 步 → 期望 ≤1）
3. `old_string` 采用率与未命中率——模型到底用不用新参数

**次指标：** pass_rate（对照组 0.733）。噪声底 ±3 题，**单轮分数差异不作为结论**。
devlog 37 已经吃过一次亏：+6.7 点看着漂亮，拆开全是方差。

## 结果

### 主指标：机制被彻底关掉了

| 指标 | 对照组 | 实验组 |
| --- | ---: | ---: |
| **自伤次数** | 13 | **0** |
| **出现自伤的题** | 6/30 | **0/30** |
| 自伤 → 被发现延迟 | 2.2 步（n=13） | 不适用（没有自伤） |
| `edit_file` 调用次数 | 63 | **47（−25%）** |
| 其中 `old_string` 模式 | 0 | **47（100%）** |
| `old_string` 未命中 | — | **0** |
| 总步数 | 350 | 325（−7.1%） |

**采用率 100% 是这次最意外的一点。** 工具描述只是把按内容定位标成 PREFERRED，
没有任何强制；模型 47 次编辑全部用了它，一次都没退回行号模式，而且**一次都没有
未命中**——说明「先读原文、再逐字给出要替换的片段」对模型来说比「数行号」自然得多。
行号模式因此在这一轮完全没有被执行到。

`edit_file` 调用数降 25% 是同一件事的另一面：以前每次自伤要额外 3–6 次编辑去修，
现在那些调用整个消失了。

### 机制链条的直接验证

devlog 37 断言那三题的步数耗尽由自伤驱动，而不是预算不够。修掉自伤之后：

- `semver_compare`：16 步用满 → **14 步 PASS**
- `cli_config_docs_contract`：18 步用满 → **9 步 PASS**（砍掉一半）
- `packaging_ci_contract`：20 步用满 → 15 步，失败原因变成隐藏测试没过

第三题尤其说明问题：它**不再耗尽步数**，露出了自己真实的死因（能力不足）。
这正是 devlog 37 说的「步数耗尽是症状不是原因」——症状消掉之后，
剩下的才是真正需要解决的东西。

### 次指标（噪声内，不作为结论）

| | 对照组 | 实验组 |
| --- | ---: | ---: |
| pass_rate | 0.733 (22/30) | 0.833 (25/30) |
| hidden_test_pass_rate | 0.833 | 0.933 |
| tokens | 1,458,155 | 1,401,267（−3.9%） |
| 翻转 | — | 7 题（5 fix / 2 regression） |

7 题翻转、噪声底 ±3 题。**+3 题在噪声带内，不能当成独立结论。**
真正的证据是主指标那张表——自伤从 13 次到 0 次不可能是采样波动。

## 诚实栏：三件对结论不利的事

**1. 回显制造了 17 次多余的 replan。** 这是上面「内核约束」那一节预告的副作用，
实测确实发生了：78 次 replan 里 17 次（22%）的触发文本以 `[编辑后]` 开头，
命中的都是回显进来的代码内容——

```
已按内容替换 service.py 的 1 处（278 -> 375 字符）。
[编辑后] 第 1-12 行（共 12 行）：
>    1 | from errors import NotFound, Unavailable      ← 命中 'error' 和 'Error'
```

一次**成功**的编辑被判成失败观察，白白花掉一次 planner LLM 调用。
根因不在本次改动，而在 `is_failure_observation` 用裸子串匹配 `error`：
任何回显或读取了含该词代码的观察都会中招（`read_file` 一直如此）。
净账仍是正的（token −3.9%、步数 −7.1%），但这是笔该还的债。

**2. 两个回归题，但主因不是这个副作用。** `filename_sanitizer`（PASS 10 步 →
耗尽 18 步）和 `normalize_users`（PASS 11 步 → 耗尽 14 步），两题的隐藏测试
**都通过了**，只是没走到 `finish`。查了 `filename_sanitizer` 的 5 次 replan，
触发原因是「文件不存在」「No module named flake8」「No module named pylint」
——它自己跑去装 linter 折腾掉了步数，与回显无关。诚实地说：这两题看起来
就是 devlog 37 反复量到的那个运行间方差。

**3. `ast.parse` 这条辅助线一次都没派上用场。** 语法检查命中 0 次。
原因不难理解：模型 100% 走了按内容定位，压根没制造出语法崩坏。
它是给行号模式兜底的，而行号模式这轮没被执行到。**保留它是为了行号模式
仍然可用时的安全网，但本次实验没有为它提供任何证据。**

## 结论

1. **按内容定位是对的修法。** 自伤归零、采用率 100%、零未命中、编辑调用少 25%、
   token 和步数都降。行号编辑的问题不是模型不小心，是接口逼着它去数一个
   每次编辑后都会漂移的量。
2. **devlog 37 的因果诊断成立。** 三道被判定为「自伤驱动」的步数耗尽题，
   修掉自伤后两题通过、一题露出真实死因。**一个正确的诊断应该能预测干预的结果，
   这次预测对了。**
3. **主指标要挑不受噪声影响的。** 这已经是第三次了：devlog 36 是违规计数、
   37 是实际用了多少步、38 是自伤次数。pass_rate 在 30 题规模下永远说明不了
   4 题以内的事。
4. **观察文本的失败判定该重做。** 裸子串匹配 `error` 让 22% 的 replan 成了误报。

## Open questions / next bets

1. **修 `is_failure_observation`。** 当前实现让任何含 `error` 字样的代码回显或
   文件读取都触发重规划。可行方向：把判定限制在观察的**结构化前缀**
   （工具自己写的那一句），而不是全文扫描；或给内核护栏文案一个显式标记位。
   这是本轮暴露出的最具体的债，且有现成的量化口径（replan 误报率 22%）。
2. **行号模式还要不要留？** 这一轮它 0 次被使用。留着是为了向后兼容和
   非文本场景，但如果后续几轮依然 0 使用，可以考虑连同 `ast.parse` 兜底一起
   简化掉——**先积累证据，不要现在就删**。
3. **pass_rate 0.833 需要 `--repeat 3` 才能确认。** 主指标已经说明机制生效，
   但「修自伤到底值多少分」这个问题，单轮回答不了。三轮的成本是 450 万 token。
4. 当前失败构成：步数耗尽 3 题（全部 `hidden_ok=True`）、隐藏测试没过 2 题。
   前者仍是最大的一栏，而 devlog 37 已经证明加预算无效——下一个假设应该指向
   「模型不知道自己还剩几步，因此不会收敛」，那是 devlog 37 open question #3。
