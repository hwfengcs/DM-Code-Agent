# 31 · Web 控制台的多轮对话：为什么是长驻子进程

**日期**：2026-08-01
**分支**：`feat/web-console`

## 背景

Web 控制台上一版的「新建运行」是一个表单 + 时间轴：填任务 → 点开始 → 看步骤 → 结束。
三个问题：

1. **不支持多轮**。每次运行是一个独立子进程，第二次运行的 agent 完全不知道第一次
   发生过什么。想接着上一轮说话，只能把上下文重新打一遍。
2. **切视图状态就没了**。运行状态和 SSE 订阅都住在 `NewRun` 组件里，`useEffect` 的
   清理函数在卸载时断流。切到会话库再切回来，条目、状态、连接全丢——看起来就像运行
   被中断了。（实际上服务端子进程一直好好活着，只是前端把自己的眼睛闭上了。）
3. 会话库只能看不能删，跑几十次之后列表就没法用了。

## 决策：给 CLI 加一个长驻会话模式

多轮对话的核心是**共享上下文**。评估过三条路：

| 方案 | 结论 |
| --- | --- |
| **长驻子进程 + stdin 投递**（选定） | 一个进程、一个 `ReactAgent`、顺序跑多轮。对话历史 / 本地记忆 / 折叠状态天然延续 |
| checkpoint + resume | ❌ 语义不对。`--resume` 是「同一个任务从第 N 步继续」，不是「带着历史开一个新任务」。硬改要动 `_run_once` 的核心语义 |
| 前端拼接历史 | ❌ 假多轮。agent 拿到的是「一段描述」而不是真的对话历史，工具调用记录、折叠状态、read-before-edit 台账全部丢失 |

选定方案**不需要改 core**——`core/agent.py` 的
`_adopt_existing_history(kind="carried")` 本来就是为「同一个 agent 实例连续 run 多次」
准备的，`cli/interactive.py` 的多轮对话模式用的就是这条路径。缺的只是一条能被 server
驱动的非交互入口。

## 协议：单向，回传走会话日志

这是这次设计里最值得记的一条。

server → 子进程：stdin 上每行一个 JSON 对象。
子进程 → server：**什么协议都没有**。

每一轮的进展、结果、失败全都从 `--trace` 的会话日志里读回来——`run_start` / `run_end`
本来就在里面。好处有三：

- 不需要发明第二套协议，也不会被 agent 自己的人类可读打印（`[plan] …`、`UI.panel`）
  污染 stdout。
- 完整复用现有的 `stream_session_lines`：实时流的代码一行没改，只是 `is_finished`
  判的从「这次运行结束了吗」变成「整个对话结束了吗」，于是一条 SSE 连接横跨全部轮次。
- 符合项目「会话日志是唯一真相源」的一贯做法。「实时看到的」与「事后审计到的」
  仍然是同一份字节。

「本轮跑完没有」= 日志里 `run_end` 的条数追平已提交的轮数。这个计数**不在内存里维护**
（那会有第二个事实来源，而且控制台随时可能在两轮之间重启），而是对 append-only 的日志
做增量扫描：只读上次之后新增的字节，结尾半行留到下次。

## 三个诚实面对的限制

1. **「结束对话」结束的是整个进程**，不是只打断当前这一轮。`ReactAgent` 没有取消接口
   ——这正是当初选子进程方案的首要理由，这里只是它的另一面。UI 上的按钮因此写
   「结束对话」而不是「停止」。
2. **上一轮没跑完不能发下一轮**（409）。ReactAgent 是单线程顺序执行的，排队只会让
   「现在到底在跑哪一轮」变得不可读。
3. **对话模式拒绝 Reflexion**。它每次 trial 会把 `conversation_history` 回滚到本轮
   开始前的快照，与跨轮累积正好相反。CLI 侧和 server 侧都硬拒——**悄悄不加这个开关
   是最坏的选择**，用户以为开着，实际没开。

写「argv 必须过真 CLI 解析器」那条断言时当场抓到一个真 bug：server 会为对话拼出带
`--enable-reflexion` 的 argv，而子进程会因互斥校验直接 exit 2，用户只会看到一个莫名
其妙失败的对话。

## 长驻带来的新责任：回收

长驻进程是这套设计唯一新增的资源泄漏面。用户开了对话直接关浏览器，进程会一直挂着
（还占着它拉起的 MCP 服务器）。所以：

- 与一次性运行**共用**并发上限（默认 2）——它们抢的是同一个工作区。
- **30 分钟空闲自动回收**，正在跑一轮的对话永不被当成空闲。
- 回收和用户主动结束都走「先关 stdin 等它自己收尾，超时才硬杀」，让 agent 有机会
  写完最后一条 `conversation_end`、保存 reflexion 记忆、正常关掉 MCP。

## 前端：状态提升到模块级 store

「切视图就停」的正解不是别处，就是把订阅的生命周期从**组件**挪到**对话**。
`web/src/lib/conversationStore.ts` 是个模块级单例（`useSyncExternalStore` 订阅），
SSE 挂在它上面。附带好处：`conversation_id` 落 `sessionStorage`，刷新浏览器后能自动
重连，`Last-Event-ID` 把断线期间的条目补回来。

对话界面本身不另存一份消息状态，而是从条目流推导（`web/src/lib/turns.ts`，纯函数，
带 vitest）。这条边界和 `entries.ts` 一样：前端只做分组，不算结论。直接后果是历史
会话也能用**同一个** `ChatTurn` 组件以对话形式打开——运行详情里新增的「对话」分区就是
这么来的，没有第二套渲染器。

对话把执行过程默认折起来了，所以必须补一个「看原文」的出口：右侧审计抽屉随时能显示
选中条目的完整 payload。**对话化不能把可审计性换掉**，那是这个项目的立身之本。

## 删除：回收站而不是 unlink

项目宪法说「原始数据永不删除」。这条说的是会话**内**的条目——append-only、折叠只
追加派生记录、原文一条不删。用户清理整个会话**文件**是另一回事，不能拿宪法当挡箭牌
拒绝一个合理需求。

折中是 `sessions/.trash/`：列表干净了，证据还在磁盘上，误删能自己拿回来。列表扫描
跳过任何点开头的子目录（不只是 `.trash`）。正在被运行中 agent 写入的会话拒绝删除
——POSIX 上删掉它只会让子进程继续写一个幽灵文件，Windows 上直接因文件锁失败。

## 验证

新增 4 个测试模块，共 42 条用例，**全部离线**：

| 文件 | 覆盖 |
| --- | --- |
| `tests/test_cli_conversation.py` | 多轮共享上下文（核心证据）、reset、单轮失败不杀会话、坏行忽略、**真子进程端到端** |
| `tests/test_server_conversations.py` | 创建 / 投递 / 忙时 409 / 跨轮 SSE / 结束 / 空闲回收 / 只读 403 |
| `tests/test_server_sessions_delete.py` | 回收站、点目录跳过、同名不覆盖、边界检查、在写拒删、批量逐条报错 |
| `web/src/lib/turns.test.ts` | 条目流 → 轮次分组 |

最关键的一条是 `test_second_turn_sees_the_first_turn`：断言第二轮发给模型的 messages
里含第一轮的任务与回答。没有这条，「支持多轮对话」就只是界面上把气泡排在一起。

真进程端到端那条 (`test_real_subprocess_carries_context_between_turns`) 用
`build_conversation_argv` 起真的 CLI 子进程、走真的 stdin 协议，provider 由
`--extension` 注入所以完全不联网——它把「server 生成的命令行」到「跨轮共享上下文」
这整条链一次性焊上了。
